# UI-слой

Декларативная модель композиции интерфейса. UI описывается как дерево узлов, каждый из которых определяет компонент, его свойства, дочерние элементы, состояния и привязки.

← [Edem](./edem.md) · Реализация: [edem-ui](../packages/edem-ui/README.md)

## Компонентный узел

Описывает один элемент UI:

- **Компонент** — имя (HTML-тег или зарегистрированный компонент)
- **Свойства** — параметры компонента (поддерживают шаблонные выражения)
- **Дочерние** — вложенные узлы, текст или перевод
- **События** — привязки к обработчикам

## Философия

Edem UI не пытается стать новым UI-фреймворком. Его задача — описывать универсальные концепции современного UI:

- композицию компонентов
- props, slots, children
- базовое локальное состояние
- привязки к данным
- события и навигацию
- layouts и route shells

Всё сложное поведение выносится наружу. Если нужен нетривиальный компонент, он реализуется как обычный пакет или локальный модуль и затем используется внутри Edem как внешний компонент.

Референсная ментальная модель — ближе к `Astro` и `Storybook`, чем к «ещё одному фреймворку».

## Внешние компоненты

UI-манифест должен уметь ссылаться не только на встроенные HTML-элементы и локальные компоненты, но и на внешние компоненты из npm-пакетов или внутренних пакетов монорепы.

Для такого компонента Edem управляет только orchestration-слоем:

- импорт и регистрация
- передача props
- привязка `v-model`-подобных значений
- маппинг events на actions, flows и navigation
- slots и children

Реализация самого компонента, его внутреннего state machine, canvas-логики, gesture handling и сложного imperative-поведения остаётся внутри пакета.

## Привязки событий

Три типа:

- **Flow** — запуск потока бизнес-логики
- **Action** — CRUD-операция над данными
- **Navigate** — навигация

Практически события покрывают базовую UI-логику: запуск мутаций, обновление локального состояния, вызов flow, переход между маршрутами и прокидывание payload из DOM или внешнего компонента в обработчик.

## Привязки данных

Итерация по коллекции:

- Коллекция-источник
- Фильтры и сортировки
- Шаблон для каждого элемента

Помимо коллекций, UI-модель должна покрывать singleton-данные, route-derived bindings, пагинацию, totals и другие базовые query-паттерны, не превращаясь в замену полноценному state manager.

## Условная отрисовка

if / elseIf / else для условного отображения.

## Структурные элементы

- **Ссылки** — обёртка в навигационный компонент
- **Модальные окна** — обёртка в модальный контейнер
- **Телепорт** — рендеринг в другую часть DOM
- **Переходы** — CSS-анимации
- **Именованные слоты** — передача контента в layout-компоненты
- **Skeleton** — индикатор загрузки
- **Empty state** — состояние пустоты

## Шаблонный движок

Разрешение выражений `{{ expr }}` в свойствах и тексте. Контекст включает: параметры маршрута, функцию перевода, данные коллекций, обработчики событий.

## Состояние и эффекты

UI-модель должна покрывать минимальный универсальный набор механизмов, характерных для Vue/React/Solid-подобных интерфейсов:

- локальные значения (`ref`-подобное состояние)
- вычисляемые значения
- синхронизацию данных и UI через наблюдение за изменениями
- базовые lifecycle/effect-сценарии

Это не попытка воспроизвести весь API конкретного фреймворка. Цель — покрыть повторяющиеся примитивы, которые нужны большинству экранов Exodus и других Edem-приложений.

## Ключевое свойство

Модель не привязана к конкретному UI-фреймворку. Одинаковые JSON-описания могут быть отрендерены на любом фреймворке (Vue, React, Svelte, или нативный DOM).

## Конкретные рендереры

JSON-дерево компонентов рендерится конкретным рендерером, который реализует фреймворк-специфичную логику. Рендерер отвечает за: разрешение шаблонных выражений в свойствах, маппинг событий (flow → запуск потока, action → CRUD, navigate → переход), условную отрисовку (if/elseIf/else), структурные элементы (teleport, transition, slots, skeleton, empty state). Один JSON — множество рендереров. Регистрация компонентов происходит через реестр: имя компонента в JSON → конкретный компонент фреймворка.

Для внешних компонентов рендерер дополнительно должен уметь работать с registry/import metadata: откуда импортировать компонент, как подключать связанные assets и как маппить модель событий конкретного фреймворка на общий Edem-контракт.

## Reactive Subscriptions

Подписки на изменения данных автоматически обновляют UI. Подписки привязаны к жизненному циклу компонентов и отписываются при уничтожении.

## Ограничения

Edem UI намеренно не решает задачи уровня специализированных widget engines. Вне области ответственности Edem-DSL:

- внутренняя реализация сложных editors
- низкоуровневая canvas-логика
- сложные анимационные state machine
- proprietary imperative runtime конкретного компонента

Такие задачи решаются на уровне внешнего пакета, который Edem использует как black-box UI building block.
