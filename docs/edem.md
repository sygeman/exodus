# Edem

Архитектура для **декларативных приложений**. Разработчик описывает приложение через структурированные манифесты, а runtime и build-time слои вместе подготавливают и исполняют это описание.

```text
Манифесты -> Build-Time Preparation -> Runtime Execution
```

## Принципы

1. **Декларативность** — разработчик описывает *что* нужно, а runtime/build-time инфраструктура определяет *как это будет подготовлено и исполнено*
2. **Разделение** — данные, логика и представление — независимые слои с чёткими контрактами
3. **Фреймворк-агностичность** — манифесты не привязаны к конкретному UI-фреймворку или языку
4. **Самореферентность** — приложение может описывать и собирать себя из своих же данных (например, [Exodus](../apps/exodus/README.md) — IDE, построенная поверх Edem)
5. **Композиция поверх переизобретения** — Edem не пытается заменить Vue, React, SolidJS или component libraries; UI-манифесты описывают композицию, базовое состояние и обёртки над существующими компонентами

## Архитектура

```text
Манифесты
       ↓
Build-Time Preparation
       ├── Парсинг -> промежуточное представление (IR)
       ├── Валидация -> ошибки и предупреждения
       └── Runtime artifacts -> metadata, bundles, bootstrap glue
       ↓
Runtime Application
       ├── Данные (хранилище + схема)
       ├── Логика (flows + triggers + effects)
       ├── Представление (screen runtime + component registry + routes)
       └── Платформа (bridge + environment)
```

**Манифест как контракт** — манифесты служат границей между слоями приложения. Data-манифест определяет структуру данных, flow-манифест — поведение, UI-манифест — структуру экрана, route-манифест — навигацию, platform-манифест — среду выполнения. Build-time слой читает эти контракты, валидирует их и подготавливает runtime artifacts. Изменение манифеста — основной способ изменить приложение.

**Граница Build-Time / Runtime** — на этапе сборки (build-time) манифесты парсятся, валидируются и преобразуются в runtime artifacts: schema metadata, route tables, registry metadata, bootstrap glue, platform configuration. На этапе выполнения (runtime) приложение работает с динамическими данными, исполняет flow, рендерит UI-манифесты и применяет effects. Build-time подготавливает контракт, runtime его исполняет.

**UI как orchestration layer** — UI-слой Edem отвечает за композицию дерева компонентов, привязку данных, маршрутов, layout, состояний и событий. Экранная логика не должна жить внутри component-local imperative кода: целевая модель — `event -> flow`. Сложное интерактивное поведение не должно заново реализовываться внутри Edem-DSL. Если нужен графовый редактор, rich text editor, сложный canvas-виджет или другой специализированный UI, он выносится во внешний пакет и подключается в Edem как обычный компонент с props, slots и events.

## Модульная система

Фундамент архитектуры — система модулей с типизированными процедурами. Модуль — именованная единица логики с контекстом, процедурами (query, mutation, subscription) и опциональной реакцией.

Реализована в пакетах: [edem-core](../packages/edem-core/README.md), [edem-data](../packages/edem-data/README.md), [edem-flows](../packages/edem-flows/README.md), [edem-ui](../packages/edem-ui/README.md).

## Зависимости между слоями

```text
┌─────────────────────────────────────┐
│            Манифесты                │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│    Build-Time Preparation Layer     │
│ Парсинг -> IR -> Валидация -> Meta │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│        Runtime Application          │
│                                     │
│  ┌─────────┐  ┌─────────┐  ┌─────┐ │
│  │ Данные  │←→│ Логика  │←→│ UI  │ │
│  └────┬────┘  └────┬────┘  └──┬──┘ │
│       └────────────┼──────────┘    │
│                    ↓               │
│            ┌──────────────┐        │
│            │  Платформа   │        │
│            └──────────────┘        │
└─────────────────────────────────────┘
```

- **Данные** — фундамент: хранение, схема, CRUD
- **Логика** — бизнес-правила и экранное поведение: flow, triggers, effects
- **UI** — представление: component tree, layouts, routes, bindings
- **Платформа** — среда выполнения: bridge, persistence, system

Модули зависят снизу вверх: UI зависит от данных и логики, логика от данных, платформа от всех.

- **Логика зависит от данных** — flow читают и записывают данные через модульный API. Выходы нод используются как входы для CRUD-операций над элементами коллекций.
- **Триггеры реагируют на события данных** — создание, обновление и удаление элементов автоматически запускают привязанные потоки. Диспетчер маршрутизирует события по шаблонам имён коллекций.
- **Выходы потоков питаются обратно в данные** — результаты выполнения нод (трансформации, вычисления, ответы внешних сервисов) записываются как значения полей элементов.
- **UI зависит от логики и данных** — screen runtime поднимает queries и state surfaces, а события маршрутизируются в flow runtime.
- **Оба слоя реализованы как модули** — данные и логика используют единую модульную систему с типизированными процедурами (query, mutation, subscription). UI runtime и platform glue строятся вокруг этих же контрактов.

**Полная цепочка реактивности** — замкнутый цикл обновлений через все слои:

```
Данные → Изменение → Emission → Диспетчер → Flow → Запись в данные → UI → Обновление
```

Изменение данных (создание, обновление, удаление элемента) генерирует событие через подписку data-модуля. Диспетчер ловит событие, маршрутизирует по шаблону имени коллекции и запускает привязанный поток. Поток выполняет бизнес-логику, результаты записываются обратно в данные. UI-слой через реактивную подписку автоматически обновляется при изменении данных. Подписки привязаны к жизненному циклу компонентов и отписываются при уничтожении.
