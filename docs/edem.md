# Edem

Архитектура для **декларативных приложений**. Разработчик описывает приложение через структурированные манифесты — build-time трансформации генерируют готовый код.

```
Манифесты → Codegen → Готовое приложение
```

## Принципы

1. **Декларативность** — разработчик описывает *что* нужно, генератор определяет *как*
2. **Разделение** — данные, логика и представление — независимые слои с чёткими контрактами
3. **Фреймворк-агностичность** — манифесты не привязаны к конкретному UI-фреймворку или языку
4. **Самореферентность** — приложение может описывать и собирать себя из своих же данных

## Архитектура

```
Манифесты (5 описаний)
       ↓
   Codegen
       ├── Парсинг → промежуточное представление (IR)
       ├── Валидация → ошибки и предупреждения
       └── Трансформации → готовые файлы
       ↓
   Готовое приложение
       ├── Данные (хранилище + схема)
       ├── Логика (потоки + триггеры)
       ├── Представление (компоненты + маршруты)
       └── Платформа (среда выполнения)
```

**Манифест как контракт** — манифесты служат границей между слоями приложения. Data-манифест определяет структуру данных, flow-манифест — бизнес-логику, route-манифест — навигацию, platform-манифест — среду выполнения. Codegen читает эти контракты и генерирует код, который их реализует. Изменение манифеста — единственный способ изменить приложение. Манифесты идемпотентны: повторное применение не меняет результат.

**Граница Build-Time / Runtime** — на этапе сборки (build-time) манифесты трансформируются в готовый код: data-слой (схема, composable-хуки), flow-бутстрап (регистрация потоков), UI-компоненты (из JSON-деревьев), platform-конфигурация (feature flags). На этапе выполнения (runtime) приложение работает с динамическими данными, выполняет потоки, рендерит UI, обрабатывает bridge-вызовы. Граница фиксирована: всё, что генерируется codegen, не изменяется во время выполнения; всё, что меняется — данные, состояние потоков, UI — живёт в runtime.

## Слои

### Слой данных

Динамическое хранилище с мета-схемой.

**Коллекции** — именованные наборы данных (аналог таблиц). Каждая коллекция определяется набором полей.

**Поля** — описания типов данных внутри коллекций. Поддерживаются типы: строки, числа, булевы, даты, JSON, файлы, изображения, видео, связи, UUID, timestamp и другие.

**Items** — единицы данных внутри коллекций. Все значения хранятся как единая структура.

**Связи** — ссылки между items разных коллекций (M2M и O2M). Поддерживают сортировку.

**Файлы** — content-addressable хранилище. Каждый файл идентифицируется хэшем содержимого. Автоматическая дедупликация. Поддерживаются миниатюры, метаданные медиа (размеры, длительность, кодеки).

**Системные возможности:**
- **Версионирование** — автоматические снапшоты перед каждым обновлением
- **Блокировки** — оптимистичная блокировка с TTL для параллельного редактирования
- **Soft deletes** — мягкое удаление с возможностью восстановления
- **Миграции** — ленивые изменения схемы (не перезаписывают данные мгновенно)
- **i18n** — строковые значения могут быть многоязычными

**Два режима:**
- **Development** — динамическая схема, полный CRUD на мета-уровне (создание/изменение коллекций и полей)
- **Runtime** — фиксированная схема, только операции с данными

**Концепции:**

- **Dynamic Schema** — схема коллекций и полей хранится отдельно от самих данных. Коллекции и поля описываются как метаданные, а единицы данных (items) — единая структура с произвольным набором значений. Это позволяет изменять структуру приложения (добавлять/удалять поля) без миграции хранилища и без потери существующих данных. Версия схемы хранится на уровне коллекции и на уровне каждого элемента для совместимости.

- **Content-Addressed Storage** — файлы идентифицируются хэшем содержимого, а не именем или идентификатором. Одинаковое содержимое всегда даёт один и тот же хэш, что обеспечивает автоматическую дедупликацию: при загрузке дубликата создаётся ссылка на существующий файл. Файлы распределяются по каталогам по двум первым символам хэша для избежания проблем с производительностью файловой системы при большом количестве файлов. Каждый файл имеет счётчик ссылок для отслеживания использования и очистки осиротевших записей.

- **In-Memory Query Engine** — фильтрация, сортировка и поиск выполняются над загруженными данными в памяти, а не на уровне базы данных. Это обусловлено тем, что данные хранятся как JSON-структуры, к которым не применимы SQL-индексы. Движок поддерживает операторы сравнения (равно, не равно, больше, меньше, содержит, начинается/заканчивается на, вхождение в диапазон/множество), логические комбинаторы (и, или) и полнотекстовый поиск по всем строковым значениям элемента. Сортировка и фильтрация учитывают локализацию: при наличии локали разрешение значения происходит до сравнения.

- **Lazy Migration** — изменения структуры данных (добавление, удаление, переименование полей, изменение типов) не применяются мгновенно ко всем элементам. Операции миграции записываются в журнал и выполняются пакетно при обращении к конкретным элементам. Это исключает простои при работе с большими объёмами данных и позволяет отложить трансформацию до момента, когда элемент фактически используется.

- **Optimistic Locking** — для параллельного редактирования элементов используется оптимистичная блокировка с временным ограничением (TTL). При блокировке указывается владелец и время жизни. Если блокировка истекла, она автоматически очищается при следующей проверке и может быть перехвачена другим процессом. Принудительное снятие блокировки доступно без проверки владельца.

- **Soft Deletes** — удаление элементов и коллекций — мягкое: устанавливается временная метка удаления, но запись сохраняется. Это позволяет восстанавливать удалённые данные. Окончательное удаление (очистка корзины) выполняется явным запросом. Все запросы автоматически фильтруют удалённые записи.

- **Singleton Collections** — коллекции с пометкой «singleton» ограничены одним элементом. Используются для хранения настроек, конфигураций и глобального состояния приложения. При первом обращении элемент создаётся автоматически с значениями по умолчанию из схемы.

- **Manifest-Driven Schema Sync** — декларативная идемпотентная синхронизация состояния базы данных с описанием в манифесте. За один проход создаются отсутствующие коллекции и поля, обновляются изменённые (тип, обязательность, метаданные, значения по умолчанию), удаляются лишние. Результат разбивается на категории: созданные, обновлённые, пропущенные — для отслеживания изменений. При добавлении новых полей в singleton-коллекции значения по умолчанию автоматически заполняются в существующий элемент.

- **Localization** — строковые значения хранятся как многоязычные объекты (ключ — код локали, значение — перевод). При чтении данных с указанием локали происходит автоматическое разрешение: приоритет — запрошенная локаль, затем локаль по умолчанию, затем первое доступное значение. Локализация учитывается при фильтрации, сортировке и полнотекстовом поиске.

### Слой логики

DAG-движок для бизнес-логики. Потоки описывают последовательность операций как граф нод, соединённых рёбрами.

**Ноды** — единицы вычислений. Типы нод по назначению:
- **Логика** —条件, ветвление, итерации, задержки
- **Данные** — входы и выходы потока
- **Трансформации** — операции над данными (set, add, multiply, append)
- **Внешние** — вызовы зарегистрированных хендлеров, вложенные потоки
- **Поток** — параллельные ветки и их агрегация

**Триггеры** — что инициирует выполнение:
- **Event** — реакция на системные события (создание, обновление, удаление данных)
- **Schedule** — выполнение по расписанию (интервал, время, дни недели)
- **Manual** — ручной запуск пользователем
- **Webhook** — HTTP callback

**State machine выполнения:**
```
pending → running → waiting → completed
                       ↓
                     error | cancelled
```

**Шаблонные выражения** — `{{ scope.path }}` для доступа к данным в контексте выполнения: входные данные триггера, выходы предыдущих нод, переменные потока.

**Особенности:**
- **Асинхронные ноды** — некоторые ноды могут приостановить выполнение и возобновить позже
- **Retries** — экспоненциальный backoff с настраиваемым количеством попыток
- **Timeouts** — ограничение времени на ноду
- **Backpressure** — лимиты на параллельные и ожидающие запуски
- **Валидация** — проверка графа на циклы, корректность ссылок, наличие триггера

**Концепции:**

- **Fork/Join** — разветвление графа на несколько веток с последующим слиянием. При достижении ноды fork граф разделяется на ветки, каждая из которых выполняется независимо. При слиянии (join) агрегируются результаты всех веток. Поддерживаются три режима агрегации: все ветки, любая ветка, N из M веток. Если какая-либо ветка содержит асинхронную ноду, выполнение приостанавливается до возобновления.

- **Async Nodes** — нода может приостановить выполнение потока и возобновить его позже через внешний вызов. Это позволяет интегрировать длительные операции (ожидание ответа от пользователя, HTTP-запрос, таймер) без блокировки всего графа. Состояние выполнения (включая промежуточные данные) сохраняется и восстанавливается при возобновлении.

- **Optimistic Sync** — при выполнении ноды action движок проверяет наличие зарегистрированного обработчика. Если обработчик есть — нода выполняется синхронно и передаёт управление следующей ноде. Если обработчика нет — нода переходит в состояние ожидания (async), и выполнение возобновляется только после внешнего вызова с предоставлением результата. Это позволяет одному и тому же потоку работать в разных режимах в зависимости от доступных обработчиков.

- **Subflows** — вложенные потоки выполняются синхронно в контексте родительского. Если дочерний поток содержит асинхронные ноды, его состояние ожидания пропагируется в родительский поток. Результат выполнения дочернего потока доступен в родительском через шаблонные выражения.

- **Template Expressions** — система разрешения выражений вида `scope.path` для доступа к данным в контексте выполнения. Три области видимости: данные триггера (входные параметры запуска), выходы нод (результаты выполнения предыдущих шагов), переменные потока (изменяемое состояние: счётчики циклов, результаты слияний). Выражения разрешаются в свойствах компонентов, тексте, условиях и конфигурациях нод.

- **Backpressure** — управление нагрузкой через лимиты на количество параллельных и ожидающих запусков одного потока. Последовательная обработка запросов через мьютекс предотвращает гонки, когда несколько одновременных запусков одновременно проверяют лимиты и превышают их. При превышении лимита запуски ставятся в очередь.

- **Retries** — при ошибке выполнения ноды автоматическое повторение с экспоненциальной задержкой. Каждая попытка увеличивает задержку (базовая × 2^(попытка-1)). Количество повторов и базовая задержка настраиваются индивидуально для каждой ноды.

- **Timeouts** — ограничение времени выполнения ноды. Если нода не завершилась за отведённое время, выполнение принудительно завершается с ошибкой. Для асинхронных нод таймаут проверяется периодически через планировщик.

- **State Machine** — полный жизненный цикл выполнения: pending (ожидание запуска) → running (выполняется) → waiting (приостановлено, ожидает внешнего вызова) → completed (успешно завершено) | error (ошибка) | cancelled (отменено). Terminal-состояния (completed, error, cancelled) не имеют переходов. Валидация переходов предотвращает некорректные смены состояний.

- **Dispatcher** — маршрутизация событий на основе шаблонов имен. Системные события (создание, обновление, удаление элементов) автоматически запускают привязанные потоки с фильтрацией по коллекции. Webhook-триггеры реагируют на HTTP-запросы по уникальным путям. При старте dispatcher строит индекс потоков по событиям и путям для быстрой маршрутизации.

- **Scheduler** — выполнение потоков по интервалам или расписанию. Интервалы задаются в минутах, часах или днях. Планировщик проверяет delayed runs и таймауты асинхронных нод с фиксированной частотой. При изменении набора потоков таймеры динамически обновляются.

### UI-слой

Декларативная модель компонентов. UI описывается как дерево узлов, каждый из которых определяет компонент, его свойства, дочерние элементы и привязки.

**Компонентный узел** — описывает один элемент UI:
- **Компонент** — имя (HTML-тег или зарегистрированный компонент)
- **Свойства** — параметры компонента (поддерживают шаблонные выражения)
- **Дочерние** — вложенные узлы, текст или перевод
- **События** — привязки к обработчикам

**Привязки событий** — три типа:
- **Flow** — запуск потока бизнес-логики
- **Action** — CRUD-операция над данными
- **Navigate** — навигация

**Привязки данных** — итерация по коллекции:
- Коллекция-источник
- Фильтры и сортировки
- Шаблон для каждого элемента

**Условная отрисовка** — if / elseIf / else для条件ного отображения.

**Структурные элементы:**
- **Ссылки** — обёртка в навигационный компонент
- **Модальные окна** — обёртка в модальный контейнер
- **Телепорт** — рендеринг в другую часть DOM
- **Переходы** — CSS-анимации
- **Именованные слоты** — передача контента в layout-компоненты
- **Skeleton** — индикатор загрузки
- **Empty state** — состояние пустоты

**Шаблонный движок** — разрешение выражений `{{ expr }}` в свойствах и тексте. Контекст включает: параметры маршрута, функцию перевода, данные коллекций, обработчики событий.

**Ключевое свойство:** модель не привязана к конкретному UI-фреймворку. Одинаковые JSON-описания могут быть отрендерены на любом фреймворке (Vue, React, Svelte, или нативный DOM).

**Конкретные рендереры** — JSON-дерево компонентов рендерится конкретным рендерером, который реализует фреймворк-специфичную логику. Рендерер отвечает за: разрешение шаблонных выражений в свойствах, маппинг событий (flow → запуск потока, action → CRUD, navigate → переход), условную отрисовку (if/elseIf/else), структурные элементы (teleport, transition, slots, skeleton, empty state). Один JSON — множество рендереров. Регистрация компонентов происходит через реестр: имя компонента в JSON → конкретный компонент фреймворка.

### Платформенный слой

Абстракция среды выполнения. Отделяет приложение от конкретной платформы (desktop, web, CLI).

**Bridge** — связь между изолированными контекстами выполнения (например, backend-процесс и UI-webview):
- **Transparent proxy** — вызовы выглядят как локальные, но выполняются в другом контексте
- **Typed messages** — запросы, ответы и события с типизированным форматом
- **Timeouts** — автоматическое завершение зависших вызовов
- **Event routing** — маршрутизация подписок по именам модулей

**System detection** — определение характеристик ОС: locale, тема (dark/light).

**Window persistence** — сохранение и восстановление геометрии окна.

**Auto-updater** — lifecycle: idle → checking → available/downloading → applying.

**Logger** — структурированное логирование с дедупликацией, меткой источника и временны́ми метками.

**Конкретные платформы** — платформенный слой реализуется через конкретные адаптеры. Каждый адаптер предоставляет: транспорт сообщений (межпроцессное взаимодействие), маршрутизацию событий (подписки на модули), system detection (locale, тема), persistence (сохранение состояния). Bridge скрывает контекст выполнения за прозрачным RPC-прокси: вызовы выглядят как локальные, но выполняются в другом процессе. Конкретная платформа определяется набором feature flags: логгер, persistence, system detection, updater, devtools, splash screen.

### Слой генерации (Codegen)

Build-time трансформация манифестов в готовый код.

**Pipeline:**
```
Манифесты → Парсинг → IR → Валидация → Трансформации → Файлы
```

1. **Парсинг** — чтение манифестов, построение типизированного промежуточного представления (IR)
2. **Валидация** — проверка перекрёстных ссылок (маршруты → компоненты, компоненты → коллекции, потоки → ноды, шаблоны → поля)
3. **Трансформации (stages)** — каждый stage генерирует подмножество файлов:
   - Хранилище и data-слой
   - Бизнес-логика и bootstrap потоков
   - UI-компоненты из JSON-деревьев
   - Конфигурация платформы
   - Конфигурация сборки
4. **Сборка зависимостей** — автоматическое объявление внешних и внутренних зависимостей
5. **Post-processing** — копирование манифестов, ресурсов, скриптов

**Генерация компонентов** — самая сложная трансформация. JSON-дерево рекурсивно преобразуется в компоненты целевого фреймворка:
- Имена компонентов → импорты
- Свойства → пропсы (с разрешением шаблонов)
- События → обработчики (с генерацией функций)
- Привязки данные → реактивные запросы
- Условия →条件ные конструкции
- Именованные слоты → slot API

**Генерация composable-ов** — для каждой коллекции:
- Reactive-обёртка над CRUD-операциями
- Автоматические подписки на изменения
- Пагинация, фильтрация, поиск (на основе метаданных коллекций)

**Генерация platform-кода** — на основе feature flags:
- Логгер, persistence, system detection, updater

**Ключевое свойство:** IR не привязан к языку. Один и тот же IR может генерировать код на разных языках и для разных фреймворков.

## Модульная система

Фундамент архитектуры — система модулей с типизированными процедурами.

**Модуль** — именованная единица логики с:
- **Контекстом** — инициализируется при старте (конфигурация, соединения)
- **Процедурами** — три типа:
  - **Query** — чтение данных (вход → выход)
  - **Mutation** — изменение данных (вход → выход)
  - **Subscription** — поток событий (выход через callback)
- **Реакцией** — опциональная инициализация после сборки всех модулей

**Сборка модулей** — несколько модулей объединяются в единый объект. Имена модулей становятся пространствами имён для процедур.

**Воркеры** — абстракция выполнения:
- **Local** — выполнение in-process (development, standalone)
- **Remote** — выполнение в другом контексте через RPC (desktop bridge)

**Вывод типов** — типы процедур автоматически выводятся из определений модулей. Полная типизация от манифестов до UI.

## Архитектурные паттерны

### Dynamic Schema

Коллекции и поля — метаданные, не структура хранилища. Позволяет менять схему без миграций хранилища. Items хранят version схемы для совместимости.

### Content-Addressed Storage

Файлы идентифицируются хэшем содержимого. Автоматическая дедупликация. Ссылочная целостность через счётчик ссылок.

### Lazy Migration

Изменения полей не перезаписывают данные мгновенно. Операции миграции записываются в журнал и применяются пакетно при обращении.

### Manifest-Driven Bootstrap

Идемпотентная синхронизация схемы из манифеста: создаёт отсутствующие коллекции/поля, обновляет существующие, удаляет лишние. Один проход.

### Transparent RPC Proxy

Вызовы удалённых процедур выглядят как локальные. Сериализация, маршрутизация и десериализация скрыты за прокси-объектом.

### Reactive Subscriptions

Подписки на изменения данных автоматически обновляют UI. Подписки привязаны к жизненному циклу компонентов и отписываются при уничтожении.

## Зависимости между слоями

```
┌─────────────────────────────────────┐
│          Манифесты (5 JSON)         │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│           Codegen (build-time)      │
│   Парсинг → IR → Валидация → Файлы │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│         Готовое приложение          │
│                                     │
│  ┌─────────┐  ┌─────────┐  ┌─────┐ │
│  │ Данные  │←→│ Логика  │←→│ UI  │ │
│  └────┬────┘  └────┬────┘  └──┬──┘ │
│       └────────────┼──────────┘    │
│                    ↓               │
│            ┌──────────────┐        │
│            │  Платформа   │        │
│            └──────────────┘        │
└─────────────────────────────────────┘
```

- **Данные** ← фундамент: хранение, схема, CRUD
- **Логика** ← бизнес-правила: потоки, триггеры, обработчики
- **UI** ← представление: компоненты, навигация, привязки
- **Платформа** ← среда выполнения: bridge, persistence, system

Модули зависят снизу вверх: UI зависит от данных и логики, логика от данных, платформа от всех.

## Зависимости между слоями данных и логики

```
Данные ← фундамент: хранение, схема, CRUD
  ↑
Логика ← бизнес-правила: потоки, триггеры, обработчики
  ↑
UI ← представление: компоненты, навигация, привязки
```

- **Логика зависит от данных** — потоки читают и записывают данные через модульный API. Выходы нод используются как входы для CRUD-операций над элементами коллекций.

- **Триггеры реагируют на события данных** — создание, обновление и удаление элементов автоматически запускают привязанные потоки. Диспетчер маршрутизирует события по шаблонам имён коллекций.

- **Выходы потоков питаются обратно в данные** — результаты выполнения нод (трансформации, вычисления, ответы внешних сервисов) записываются как значения полей элементов.

- **Оба слоя реализованы как модули** — данные и логика используют единую модульную систему с типизированными процедурами (query, mutation, subscription). Модули собираются в единый объект, имена модулей становятся пространствами имён для процедур.

**Полная цепочка реактивности** — замкнутый цикл обновлений через все слои:
```
Данные → Изменение → Emission → Диспетчер → Flow → Запись в данные → UI → Обновление
```
Изменение данных (создание, обновление, удаление элемента) генерирует событие через подписку data-модуля. Диспетчер ловит событие, маршрутизирует по шаблону имени коллекции и запускает привязанный поток. Поток выполняет бизнес-логику, результаты записываются обратно в данные. UI-слой через реактивную подписку автоматически обновляется при изменении данных. Подписки привязаны к жизненному циклу компонентов и отписываются при уничтожении.
